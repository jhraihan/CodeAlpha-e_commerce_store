# CLAUDE.md

Guidance for Claude Code when working in this repository.

## Project

A simple e-commerce store: product listings, product detail pages, a shopping cart, user registration and login, and order processing. Built with Django 6.0, PostgreSQL, Django templates, plain CSS, and vanilla JavaScript.

Full requirements live in `PRD.md`. Read it before adding a feature. It defines the data model, the URL map, the security requirements, and what is explicitly out of scope.

## Code Style

### No comments

Write no comments in any code file. No inline comments, no block comments, no docstrings, no file headers, no `TODO` or `FIXME` notes, no commented-out code.

This applies to every file type: `.py`, `.html`, `.css`, `.js`, `.sql`, and config files.

If a piece of code needs a comment to be understood, rewrite it until it does not. Use a clear function name, a named variable for an intermediate value, or an early return. Naming is the explanation.

```python
if order.status == "pending" and order.created_at < cutoff:
    ...
```

```python
is_stale_pending_order = order.status == "pending" and order.created_at < cutoff
if is_stale_pending_order:
    ...
```

The one exception: text that is part of the product, not an explanation of the code. Django migration files are generated, leave them as they come. Form field labels, help text, template copy, and user-facing error messages are content and stay.

Where a decision is genuinely non-obvious and the reason cannot live in a name, put the reason in `PRD.md` or in the commit message. Do not put it in the source.

### Human-written

The code should read as though one developer wrote it by hand.

- No "Generated by", "Created with", or AI attribution anywhere in a file.
- No over-explaining through excessive naming: `user` not `user_object_instance`.
- No defensive scaffolding for cases the PRD rules out. There are no product variants, so do not write code that anticipates them.
- No abstraction with a single caller. Write the direct version; extract only on the second real use.
- Consistent style throughout: if one view uses a Django class-based view, do not write the next as a function view without a reason.
- Keep functions short enough to read at once. A view that runs past roughly 40 lines is doing too much.
- Follow PEP 8 for Python. 4-space indent, `snake_case` for functions and variables, `PascalCase` for classes.

### Clear

- Use full words in names. `quantity`, not `qty`. `product`, not `prod`.
- Prefer a plain `for` loop over a comprehension that no longer fits on one line.
- Return early rather than nesting `if` blocks.
- One responsibility per function.
- Use `Decimal` for all money. Never a float.

## Project Structure

Keep this layout. Do not add directories, apps, or layers beyond it without being asked.

```
e-commerce-store/
    manage.py
    requirements.txt
    .env
    .env.example
    .gitignore
    PRD.md
    CLAUDE.md
    config/
        settings.py
        urls.py
        wsgi.py
    store/
        models.py
        views.py
        urls.py
        forms.py
        admin.py
        cart.py
        migrations/
    accounts/
        views.py
        urls.py
        forms.py
    templates/
        base.html
        accounts/
            login.html
            register.html
        store/
            product_list.html
            product_detail.html
            cart.html
            checkout.html
            order_detail.html
            order_list.html
    static/
        css/style.css
        js/cart.js
    media/products/
```

Two apps only. `store` owns the catalog, the cart, and orders. `accounts` owns registration and login.

Where things go:

| Kind of change | File |
|----------------|------|
| New database field or table | `store/models.py`, then a migration |
| New page | a view in `store/views.py`, a route in `store/urls.py`, a template in `templates/store/` |
| Form validation | `store/forms.py` or `accounts/forms.py` |
| Cart logic | `store/cart.py` |
| Admin panel behavior | `store/admin.py` |
| Styling | `static/css/style.css` |
| Browser behavior | `static/js/cart.js` |

Do not create a `utils.py`, a `services/` layer, a `helpers/` module, or a REST API. The project is small enough that logic belongs in the view, the model, or `cart.py`.

## Technical Rules

- Python 3.12, Django 6.0, PostgreSQL. Database access through the Django ORM.
- No frontend framework, no build step, no bundler, no npm. Vanilla JavaScript only.
- No CSS framework. One hand-written `style.css`.
- Keep `requirements.txt` to what the PRD lists. Ask before adding a dependency.
- Schema changes go through `makemigrations` and `migrate`. Never hand-edit a migration that has been applied.
- The cart lives in the session, not the database.
- Secrets come from environment variables via `.env`. Never hardcode `SECRET_KEY`, a database password, or any credential. Never commit `.env`.
- Checkout runs inside a single transaction and re-reads stock and price from the database. Never trust a price or quantity that arrives in the request.
- Leave Django's CSRF protection and template auto-escaping on. Do not apply the `safe` filter to text entered by a user or by staff.
- Order queries are filtered by the logged-in user.

## Git

Commits are authored by the repository owner alone.

- Do not add a `Co-Authored-By` trailer for Claude or any AI tool.
- Do not add "Generated with Claude Code" or similar to a commit message or a pull request description.
- Do not add `Co-Authored-By` for anyone the user did not name.

Commit messages: a short imperative subject line, lowercase, no trailing period. Add a body only when the reason for the change is not obvious from the diff. This is where the reasoning that is kept out of the code belongs.

```
add stock check to checkout transaction

Cart quantities live in the session, so the client can influence them.
Re-reading stock inside the transaction keeps an oversell from writing a
partial order.
```

Commit or push only when asked.
